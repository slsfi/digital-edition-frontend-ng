# v4 breaking changes and fork migration notes

> [!NOTE]
> These notes describe the breaking changes introduced in **v4.x.x** of the base app and assume the fork is on the **latest v3 release**. Earlier breaking changes are documented in the [v2](v2.md) and [v3](v3.md) notes.

The Stage 2 application-builder and Vitest migration is complete; its breaking changes are planned for v4. The release has not yet been tagged. Use the final v4 release notes and tagged source when upgrading a production fork.

## 1. Prepare the fork

The latest v3 release includes the standalone and zoneless application changes released in v3.1.0. Forks still on v3.0.x need to account for those earlier changes as part of their upgrade; review the v3.1.x release notes in the [changelog](../../CHANGELOG.md) as well.

Use the fork's normal `base`/`production` branch workflow described in [deployment](../DEPLOYMENT.md#updating-from-the-base-app-digital-edition-frontend-ng). Merge the v4 upstream changes into a working branch for the edition and review them before deploying. Preserve the existing production image/tag for rollback.

Inventory the fork's customizations before resolving conflicts. Typical files are configuration, global overrides, public assets, `src/index.html`, `angular.json`, stylesheet inclusions, TEI inclusions, translations, and crawler documents. Some forks also customize routes, services, the Express server, tests, or deployment scripts.

Combine the new upstream build/server/test structure with the edition's own settings. Selecting the upstream version of an entire configuration file can discard edition settings; selecting the fork's version can retain removed tooling. In particular, preserve the fork's locales, public/backend origins, auth options, enabled features, menus, custom routes, and styles.

The supported runtime is Node `^24.15.0` with npm `>=11.16.0`, as declared in [package.json](../../package.json). If the fork already uses a supported Node 24 runtime, it can keep it. Merge the dependency manifest and lockfile together and use `npm ci` to install the resulting versions.

## 2. Relocate configuration, styles, and public files

Apply this mapping to the edition's own files, including extra assets that are absent from the base app:

| v3 location | v4 location |
| --- | --- |
| `src/assets/config/config.ts` | `src/project/config.ts` |
| `src/assets/custom_css/custom.scss` | `src/project/global-overrides.scss` |
| `src/global.scss` | `src/styles.scss` |
| `src/assets/fonts/` | `public/assets/fonts/` |
| `src/assets/images/` | `public/assets/images/` |
| `src/assets/ebooks/` | `public/assets/ebooks/` |
| `src/assets/files/` | `public/assets/files/` |
| `src/assets/icon/favicon.ico` | `public/favicon.ico` |
| `src/robots.txt` | `public/robots.txt` |
| `src/sitemap.txt` | `public/sitemap.txt` |
| `src/static-html/` | `public/static-html/` |

Carry over the fork's configuration and overrides rather than replacing them with the base app's defaults. The exported `config` object, setting names, and `@config` imports are preserved; the alias in `tsconfig.json` now points to `./src/project/config`. Update fork-owned direct imports, file replacements, generator scripts, and CI commands that use the old filesystem paths. Ignored local configuration variants now belong in `src/project/config-*.ts`; relocate any existing ignored files separately, since Git does not move them as part of a merge.

Keep the fork's commented-out stylesheet inclusions when renaming `global.scss`. The global `styles` array in `angular.json` must retain this order:

```json
"styles": [
  "src/styles.scss",
  "src/project/global-overrides.scss"
]
```

`src/index.html`, `src/theme/_inc-global-tei.scss`, the other shared theme files, and `src/locale/` retain their locations. See [theming](../THEMING.md) for the current styling extension points.

Update relative Sass font references. Files under `src/theme/font-face/` now use `../../../public/assets/fonts/...`. Angular still processes these CSS resources and emits hashed font files under each locale's `media/` output directory. Custom stylesheets at other directory depths need the corresponding relative source path.

Merge the new Angular asset rules: copy `public/` to the browser output root, copy `public/favicon.ico` to `assets/icon` as a compatibility alias, and retain the Ionicons SVG rule. Remove the broad `src/assets/` copy rules. Move additional fork asset-copy rules to their new source locations as appropriate. Configuration and SCSS remain compiled source inputs under `src/` and are no longer served as raw public files.

### Public URLs and generated documents

The source moves preserve existing public `assets/...` and `static-html/...` URLs. For example, a file moved to `public/assets/images/about-pages/example.jpg` remains available at both `/sv/assets/images/about-pages/example.jpg` and `/assets/images/about-pages/example.jpg` when Swedish is an emitted locale and the configured default. The unprefixed request uses the default locale's output without redirecting. Existing asset links in configuration, templates, and backend content can remain unchanged.

The favicon link in `src/index.html` now uses relative `favicon.ico`, resolved against the locale's base href. The former `assets/icon/favicon.ico` address remains available from the same source file.

`npm run generate-sitemap` writes `public/sitemap.txt`; `npm run generate-static-collection-menus` writes `public/static-html/collection-toc/`. Their configuration flags and auth behavior are preserved. Merge the new generated-menu Git ignore rules and carry over ignored local output or regenerate it. Docker still runs both generators before building.

`public/robots.txt` and `public/sitemap.txt` are copied into every emitted locale directory. The existing nginx root-file rule and Express unprefixed static router serve `/robots.txt` and `/sitemap.txt` from the configured default locale. Keep those rules when merging fork deployment changes; the crawler document URLs stay at the website root.

## 3. Merge the integrated build and locale configuration

[`angular.json`](../../angular.json) changes structurally, so forks with customized build, locale, or test settings should expect merge conflicts. Preserve the fork's locale set and project-specific options while adopting these targets:

| Target | v4 builder |
| --- | --- |
| `build` | `@angular/build:application` |
| `serve` | `@angular/build:dev-server` |
| `test` | `@angular/build:unit-test` |
| `extract-i18n` | `ng-extract-i18n-merge:ng-extract-i18n-merge`, delegating to `@angular/build:extract-i18n` |

Merge the former browser/server build settings into the application build. Its principal entry/output options are:

```json
"outputPath": {
  "base": "dist/app",
  "browser": "browser",
  "server": "server"
},
"browser": "src/main.ts",
"server": "src/main.server.ts",
"outputMode": "server",
"ssr": {
  "entry": "src/server.ts"
}
```

The old browser `main` option is now `browser`. The `server` option names the Angular bootstrap; `ssr.entry` names the Express entry. Remove the separate `server`, `serve-ssr`, and `prerender` targets. Remove unsupported Webpack options such as `buildOptimizer`, `vendorChunk`, and the old locale-specific `deleteOutputPath` overrides. Preserve environment/route file replacements, budgets, and fork-owned supported options. Production critical CSS inlining remains disabled with `optimization.styles.inlineCritical: false`; the application uses runtime SSR and does not add prerendered routes.

### Preserve the edition's languages and URL prefixes

Retain the fork's translation files, translated locale set, locale-specific configurations, and production `localize` list. The base app's Swedish/Finnish list is an example, not the required locale set for every fork. Keep the technical `sourceLocale: "aa"` unless the fork deliberately uses a different source-locale setup; it is not the default public language.

Convert each locale's old `baseHref` setting to the equivalent `subPath`. For example:

```json
"sv": {
  "subPath": "sv",
  "translation": "src/locale/messages.sv.xlf"
}
```

Use the edition's actual URL subpath, which may differ from its Angular locale code. Keep any deployment-wide `build.options.baseHref` when the site runs under a directory prefix. Merge locale overrides and extraction `targetFiles` according to the fork's own translations.

Check that `config.app.i18n.languages` and `defaultLanguage` still match the intended deployment. Unprefixed requests use the configured default language when it was emitted, falling back to the first emitted locale otherwise. They do not redirect based on `Accept-Language`. A single-locale fork is supported. Set nginx's `$default_locale` to the emitted output subpath used for the default language; review any custom nginx paths if that subpath is empty or nested.

Distinguish the HTTP response from browser navigation when testing compatibility: an unprefixed request receives default-language HTML without an HTTP redirect, while browser bootstrap can normalize the URL to the document's locale base href. In the base app this places the route under `/sv/`, as it did before the migration.

### TypeScript and localization setup

Server and browser sources now share `tsconfig.app.json`; `tsconfig.server.json` is removed. Carry any necessary fork compiler settings into the application config. The base includes `src/**/*.ts`, excludes specs and `src/test-setup.ts`, and retains Node/localization types and extended diagnostics. There is no separate application `files` list. `tsconfig.json` keeps `ES2022` modules, `bundler` resolution, strict checks, `resolveJsonModule`, and `esModuleInterop`; the redundant `allowSyntheticDefaultImports` entry is removed. Root helper scripts remain CommonJS, so this migration does not require adding `"type": "module"` to the root package.

Application polyfills include `@angular/localize/init` and the centralized `src/ionicons-polyfill`. Preserve both for application and test builds. Do not restore Zone.js or add client hydration during this merge; the v3.1 standalone/zoneless architecture and non-hydrated SSR remain in use.

`npm run extract-i18n` continues to sort and merge XLIFF 2 files under `src/locale/`. Merge the wrapper's `builderI18n` change and retain the fork's target translation files. Review extraction output before committing translation changes.

## 4. Reapply custom SSR code and request handling

| v3 implementation | v4 implementation |
| --- | --- |
| Root `server.ts` | `src/server.ts` |
| `CommonEngine` | `AngularNodeAppEngine` |
| Separate locale launchers and `proxy-server.js` | One emitted `dist/app/server/server.mjs` entry with Angular locale dispatch |
| Locale browser `index.html` shells | `index.csr.html` shells |
| Express request injection into app services | `APPLICATION_REQUEST_CONTEXT` from the Angular Web `REQUEST` adapter |
| Express response injection for HTTP status | Angular's nullable `RESPONSE_INIT` |
| Custom Express auth CSR-shell handling | Generated Angular `RenderMode.Client` routes |

Reapply fork middleware customizations to [`src/server.ts`](../../src/server.ts). Keep Express app creation, middleware registration, the Angular handler, and the exported CLI request handler aligned with the new entry. Code using CommonJS server globals such as `__dirname` or `require` needs ESM-compatible equivalents; the base resolves paths from `import.meta.url`.

Preserve the ordering of static serving, missing-static-file 404s, and probes before the SSR rate limiter and Angular handler. Keep the default static router's localized and unprefixed mounts, the ebook dynamic-route exception, and `Vary: User-Agent` handling. Locale metadata comes from the fork's Angular configuration and emitted output, rather than a hardcoded language list. The server listener starts only when the emitted entry runs directly, allowing the Angular dev server to import its handler.

Fork services that inject the old repository Express `REQUEST`/`RESPONSE` tokens must be adapted. Use optional [`APPLICATION_REQUEST_CONTEXT`](../../src/app/tokens/request-context.token.ts) injection for the app-relative request URL, resolved public origin, and user agent. The [server adapter](../../src/ssr/server-request-context.ts) reads Angular's nullable Web `REQUEST` and strips the locale/deployment base path while preserving query parameters and escaped characters. Keep browser router/document/navigator fallbacks when the context is absent. Express-specific properties and methods are not part of Angular's Web `Request`; keep server-only adaptation under `src/ssr/`.

For HTTP status changes, optionally inject `RESPONSE_INIT` from `@angular/core` and set its `status` only when it is present. Review custom not-found or error pages for the appropriate browser and HTTP response behavior.

### Generated server routes and authentication

Continue editing `src/app/app.routes.ts` and fork-owned lazy route files as the canonical route source. `npm run generate-routes` now produces two ignored outputs:

- `src/app/app.routes.generated.ts`: production browser routes, filtered according to feature settings.
- `src/app/app.routes.server.generated.ts`: Angular server-rendering metadata consumed by `app.config.server.ts`.

The old `auth-protected-route-paths.generated.ts` output is removed. Regenerate outputs rather than editing them manually, and update fork scripts that consume the removed artifact.

When auth is enabled, generated server routes select client rendering for protected parents and children while public routes retain SSR. Merge `provideServerRendering(withRoutes(serverRoutes))` and the server request-context provider into `app.config.server.ts`, preserving fork-owned providers and browser/server service overrides. Keep auth guards and verify fork-specific protected routes, including parameterized and nested routes. Preserve the intentional `IonicServerModule` provider bridge and the browser's idle-time route preloading strategy.

### Proxy and public-origin settings

Carry the edition's `app.siteURLOrigin` into the new configuration and review `app.ssr.trustProxyHops` together with the new `app.ssr.trustedProxyAddresses`. Defaults are two hops and `["loopback", "linklocal", "uniquelocal"]`. For HAProxy -> nginx -> Node, retain two hops when that reflects the actual deployment; Node's immediate nginx peer and the trusted proxy addresses must fit the configured ranges. Add actual public proxy IPs/CIDRs when a trusted hop uses them. An empty address list or zero hops disables proxy trust.

Express uses both the hop limit and address list for client-IP resolution. Origin forwarding headers are accepted only from a trusted immediate peer; Angular handles the configured forwarding headers. Merge custom proxy changes so upstream proxies overwrite client-supplied origin headers and preserve the public HTTPS scheme. Angular's host allowlist includes loopback hosts and the configured site hostname; supply extra deployment aliases through `NG_ALLOWED_HOSTS` where needed. See [deployment](../DEPLOYMENT.md#deployment) for the current operational settings.

## 5. Convert fork-owned tests to Vitest

Angular unit tests now use Vitest and jsdom through `@angular/build:unit-test`. Merge the new test target and `tsconfig.spec.json` (`vitest/globals` and localization types). Remove Karma target options, `karma.conf.js`, and the manual `src/test.ts` TestBed bootstrap. The builder initializes TestBed and inherits application styles/assets/polyfills. Keep `src/test-setup.ts` to restore spies and real timers after each test. Unit tests no longer need a Chrome installation or Karma browser flags; browser integration checks remain useful separately.

All upstream specs are converted. Convert the fork's additional or modified specs as part of resolving conflicts:

| Jasmine API | Vitest equivalent |
| --- | --- |
| `jasmine.createSpy()` | `vi.fn()` |
| `spyOn(object, 'method')` | `vi.spyOn(object, 'method')` |
| `.and.returnValue(value)` | `.mockReturnValue(value)` |
| `.and.callFake(fn)` | `.mockImplementation(fn)` |
| `.calls.count()` / `.calls.allArgs()` | `.mock.calls.length` / `.mock.calls` |
| `toHaveBeenCalledOnceWith(...)` | `toHaveBeenCalledTimes(1)` plus `toHaveBeenCalledWith(...)` |
| `jasmine.clock().install()` / `.uninstall()` | `vi.useFakeTimers()` / `vi.useRealTimers()` |

Replace Jasmine-specific matchers, clock behavior, and spy types rather than assuming identical semantics. `vi.spyOn()` calls the original method by default, so set a mock implementation where the old Jasmine spy was intended to stub it. Preserve typed service fakes and real signal properties; use Vitest mock types for mocked methods.

Replace Zone-dependent `fakeAsync`, `tick`, and `waitForAsync` usage with native async tests or Vitest fake timers. Advance scheduled rendering work before waiting for `fixture.whenStable()` with mocked timers. Keep localization and centralized Ionicons registration inherited from the application polyfills, and add fork-owned icons centrally rather than in component constructors. See [development testing](../DEVELOPMENT.md#testing) and the converted upstream specs for current patterns.

`npm test` retains interactive watch mode; `npm run test:ci` runs once with jsdom. Replace fork CI commands that pass `--browsers=ChromeHeadless`, invoke the removed Karma configuration, or use the removed `ci` configuration of the Angular test target (`ng test --configuration=ci`) with `npm run test:ci`. The npm script supplies `--watch=false`; it does not depend on a named Angular test configuration.

## 6. Merge dependencies, runtime commands, and deployment changes

Merge `package.json` and `package-lock.json` together, retaining genuinely needed fork dependencies. Important tooling changes are:

- Keep `@angular/build`; remove `@angular-devkit/build-angular` once all fork targets use the new builders.
- Add `vitest` and `jsdom`.
- Remove direct Jasmine/Karma dependencies: `@types/jasmine`, `jasmine-core`, `karma`, `karma-chrome-launcher`, `karma-coverage`, `karma-jasmine`, and `karma-jasmine-html-reporter`.
- Remove obsolete `browser-sync` and `istanbul-lib-instrument` dependencies, unless separate fork tooling still explicitly needs them.

Use the versions and install-script approvals in the selected v4 release instead of recreating the lockfile against unrelated newer versions.

| Command or output | v4 behavior |
| --- | --- |
| `npm start` / `npm run start:fi` | Generate routes, then serve one development locale at `/` with SSR and hot updates. |
| `npm run build:ssr` | Generate routes, then run one integrated production browser/server build. |
| `npm run serve:ssr` | Run `node dist/app/server/server.mjs` on port 4201, or `PORT`. |
| `npm run ssr-start` | Build and then serve the production output. |
| Browser output | `dist/app/browser/<locale subPath>/`, including `index.csr.html`. |
| Server output | `dist/app/server/`, with one runtime entry and localized Angular bundles. |

Common legacy command mappings are:

| v3 command | v4 command |
| --- | --- |
| Separate browser build followed by `ng run app:server:production` | `npm run build:ssr` |
| `node dist/app/proxy-server.js` | `npm run serve:ssr` |
| `ng test --configuration=ci` or a Karma/headless-Chrome command | `npm run test:ci` |

`prestart` and `prestart:fi` run automatically when invoking the corresponding npm start scripts. Fork-owned start commands also need route generation; direct `ng serve` calls must generate routes beforehand. The development server now executes SSR, so exercise custom code that previously ran only in the browser. Production output remains the relevant environment for multi-locale dispatch and deployment verification.

`proxy-server.js` and `postbuild-copy-files.js` are removed. Remove custom calls to them, separate `ng run app:server...` builds, and the legacy prerender target. Carry any fork-owned extra copy operations into supported asset rules or a separate fork script. Adapt launchers, process-manager definitions, benchmark scripts, Docker commands, and CI paths to the canonical `serve:ssr` entry. The Docker runtime already uses that npm command.

The browser volume remains `/digital-edition-frontend-ng/dist/app/browser` in the supplied image and `/static` in nginx. Keep the fork's image repository, ports, locale settings, and proxy configuration while merging the new Docker/nginx setup. nginx must cache hashed fonts emitted under locale `media/` directories. `npm run compress` still processes the entire `dist/app/browser` tree; WOFF/WOFF2 are already compressed and stay excluded from its gzip include list.

Validate with a fresh browser volume before deploying the new image: an existing named volume retains old files when its image changes. Follow [deployment instructions](../DEPLOYMENT.md#deployment) for the fork's rollout and volume replacement. Preserve the previous image/tag and use the normal [rollback procedure](../DEPLOYMENT.md#roll-back-to-earlier-version) if deployment validation fails.

## 7. Verify the edition before deploying

Run the fast checks from the merged fork:

```bash
npm ci
npm run test:ci
npm run test:source-encoding
npm run test:routes-parser
npm run test:static-collection-menus
```

Run `npm run extract-i18n` when validating the extraction merge and inspect any translation diff. Generate the fork's sitemap and static menus as appropriate for its prebuild/auth flags before the local production build; Docker runs the generators automatically.

```bash
npm run generate-sitemap
npm run generate-static-collection-menus
npm run build:ssr
npm run test:build-output
npm run test:ssr:checks
npm run test:ssr:server
```

`test:ssr:server` includes its own production build. When the preceding build is already current, `node scripts/test-ssr-server.js` runs the same emitted-server checks without rebuilding.

Start the built app:

```bash
npm run serve:ssr
```

In another terminal, run SSR checks using the fork's own routes/locales. The default smoke fixtures target base-app content; use a JSON cases file for other editions:

```bash
npm run test:ssr:smoke -- --cases-file=path/to/edition-cases.json
```

Add `--auth-enabled` when checking an auth-enabled build. JSON case files accept literal `includes` checks, not user-provided regex patterns; see [smoke-test options](../DEVELOPMENT.md#ssr-smoke-test-local-or-remote). Test auth-enabled and disabled configurations separately if the fork supports both. Run `test:ssr:benchmark` if the fork customizes benchmark or runtime-launch tooling.

Finally verify the actual deployment shape, including the production image behind the fork's nginx configuration:

- Every production locale, its configured URL prefix, and unprefixed default-language responses. Include single-locale or custom-subpath builds used by the edition.
- Public SSR pages, protected CSR shells, login/redirect behavior, missing routes/static files, and dynamic ebook routes.
- Canonical/Open Graph URLs, public HTTPS origin behind the real proxy chain, and HTTP 404/429 responses.
- Edition images, files, ebooks, fonts, icons, both favicon paths, generated menus, and root `/robots.txt` and `/sitemap.txt` responses.
- nginx cache headers, gzip delivery, and a browser volume populated from the new image.
- Browser navigation, idle route preloading, and development SSR/hot updates for custom pages and global styles.

Record the fork-specific checks in the upgrade PR before deploying. Use [project customization](../PROJECT-CUSTOMIZATION.md) for edition settings and customization files, [theming](../THEMING.md) for styling, and [deployment](../DEPLOYMENT.md) for operating procedures. Base-app implementation and testing details remain in [development](../DEVELOPMENT.md).
