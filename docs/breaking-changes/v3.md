# v3 breaking changes and fork migration notes

> [!NOTE]
> These notes describe the breaking changes introduced in **v3.x.x** of the base app and assume the fork is on the **latest v2 release**. Forks on v1 also need to review the [v2 notes](v2.md) and any earlier changes missing from their source.

The main runtime and styling changes were released in [v3.0.0](../../CHANGELOG.md#300--2026-09-07). [v3.1.0](../../CHANGELOG.md#310--2026-09-21) subsequently moves the application to standalone Angular/Ionic APIs and zoneless change detection. Most configuration-only forks retain their behavior, but forks with custom application code and icons need additional adaptation.

Paths and commands below refer to the v3 source layout. The [fork update workflow](../DEPLOYMENT.md#updating-from-the-base-app-digital-edition-frontend-ng) brings in the current upstream `main`; when merging v4 or later source, review its notes too. In particular, v4's file moves, integrated application builder, and Vitest migration are covered in the [v4 document](v4.md).

## 1. Update Node, npm, and build infrastructure

v3 requires Node.js `^24.15.0` and npm `>=11.16.0`. A Node 20/22 environment supported by v2 no longer meets these requirements.

Update local development, custom CI, and Docker build images together. Merge the runtime declarations, dependencies, lockfile, and npm install-script approvals from `package.json`, while preserving the edition's package identity and custom scripts. Install with `npm ci` using the supported runtime. The upstream Docker build moves to Node 24, and `gzipper` moves to a version requiring Node 24.

Angular moves from v20 to v22 and Ionic from v8 to v9. Adopt the corresponding upstream TypeScript/build changes rather than updating only the package versions. Supported browsers follow the Angular major version; check the edition in the browsers supported by the target release. Forks with customized GitHub Actions workflows also need to reconcile the updated actions, including `actions/checkout`.

## 2. Review changed home-page defaults

v3.0.0 introduces home-page CSS variables with inline defaults and changes several visual defaults:

| Area | Previous default | v3 default |
| --- | --- | --- |
| Site presentation in landscape mode. | Center-aligned text. | Start-aligned text. |
| Banner title and subtitle background. | Main background color at `0.8` opacity. | Transparent background at full opacity. |
| Text content width and placement. | Main sections up to `1000px` wide. | Centered content column up to `750px` wide. |
| Site title, subtitle, and footer in portrait mode. | Start-aligned. | Centered. |
| Search bar in wide portrait mode. | Start-aligned. | Centered. |

Review the edition in both orientations and at narrow and wide viewport widths. Keep deliberate fork overrides and use the new CSS variable reference in `src/assets/custom_css/custom.scss` to adjust the defaults. For example, this restores the earlier banner background/opacity and requests a wider content column:

```scss
page-home {
  --banner-title-background-color: var(--main-background-color);
  --banner-title-opacity: 0.8;
  --text-content-max-width: 1000px;
}
```

This is a starting point for those properties, not a complete recreation of the old layout. Review alignment, spacing, and responsive behavior separately. The v3 defaults are defined where the variables are consumed in `src/app/pages/home/home.page.scss`; place edition overrides in `custom.scss` rather than editing the shared page styles.

## 3. Move customizations out of removed scoped-variable partials

v3.0.0 moves several scoped CSS variable defaults to inline fallbacks. The defaults and supported override selectors remain compatible, so existing overrides in `src/assets/custom_css/custom.scss` can stay there.

These partials under `src/theme/scoped-variables/` are removed:

| Removed partial | Affected area |
| --- | --- |
| `_info-overlay-variables.scss` | Info overlays. |
| `_page-elastic-search-variables.scss` | Elastic search. |
| `_page-index-variables.scss` | Indices. |
| `_page-text-variables.scss` | Text variants. |
| `_semantic-code-variables.scss` | Semantic highlighting. |
| `_text-changer-variables.scss` | Text changer. |
| `_top-menu-variables.scss` | Top menu. |

If the fork edited one of these files, move its changed CSS custom property values into `custom.scss` under the selector listed in the override reference. Remove custom imports of the deleted partials. If a customization needs a shared fallback change, reconcile it with the new consuming stylesheet instead of recreating the old partial.

The unused `--top-menu-logo-height` variable is removed. Review any fork override of it; the base app no longer consumes it. Unused `ion-datetime` and `ion-datetime-button` styles are also removed. Forks that added those components need to retain the styles their own UI requires.

See [theming](../THEMING.md#customize-css-variables) for the current override approach. That guide uses v4 filenames; in v3 the override file remains `src/assets/custom_css/custom.scss`.

## 4. Keep TEI styling aligned with backend HTML

v3.0.0 adds an optional second set of TEI styles. The "v2" in this TEI style name describes the TEI styling variant, not base-app release v2.

The default `src/theme/_inc-global-tei.scss` remains available. To choose the alternate styles in a v3 fork, change the inclusion in `src/global.scss` to `theme/inc-global-tei-v2`. Those styles require a different HTML structure, so switch only when the edition's backend text HTML matches it. Preserve the edition's selection of individual TEI features when merging either entry file.

[v3.0.1](../../CHANGELOG.md#301--2026-09-08) fixes a Sass variables import path in the alternate styles. Include that fix when using them. See [TEI styling](../THEMING.md#tei-styles) for current guidance.

## 5. Adapt custom Angular code for v3.1

The standalone and zoneless migration is introduced in **v3.1.0**, rather than v3.0.0. Configuration, public route behavior, theming contracts, build commands, deployment, and output layout remain stable within this migration. The main work for a fork is reconciling custom bootstrap, components, providers, tests, and icons.

### Bootstrap, providers, and routes

Both `src/main.ts` and `src/main.server.ts` now bootstrap `AppComponent` with `bootstrapApplication()`. Application-owned NgModules and page/routing NgModules are removed.

| Previous customization location | v3.1 destination |
| --- | --- |
| Browser/shared providers in `src/app/app.module.ts`. | `src/app/app.config.ts`. |
| Server providers in `src/app/app.server.module.ts`. | `src/app/app.config.server.ts`, merged after the shared browser configuration. |
| Route registration in `src/app/app-routing.module.ts`. | The router providers in `app.config.ts` and canonical `src/app/app.routes.ts`. |
| Lazy page NgModules and their routing modules. | Standalone page components with `loadComponent`, or standalone `Routes` arrays with `loadChildren` where multiple/child routes are needed. |

Move fork-owned providers into the appropriate configuration file. Preserve platform-specific browser/server service substitutions, route reuse, preloading, guards, and the edition's router options. Keep custom routes in the canonical source and regenerate production routes; do not restore removed NgModules to avoid a merge conflict.

### Standalone components and Ionic imports

Fork components must declare their template dependencies in their own `imports`, including Angular directives/pipes, child components, and Ionic standalone components from `@ionic/angular/standalone`. Remove custom components from NgModule `declarations` and update tests to import them into TestBed.

Application Ionic providers are registered with `provideIonicAngular()`. The server keeps `importProvidersFrom(IonicServerModule)` as the intentional bridge to Ionic's server providers. Preserve this server setup when merging custom provider code.

### Zoneless state and tests

Zone.js is removed from browser, server, and test setup, and the application no longer installs `provideZoneChangeDetection()`. Custom code that depended on patched timers, promise callbacks, or manual DOM callbacks triggering a render must notify Angular of template-state changes.

Use signals, template inputs, the `async` pipe, or explicit Angular change-detection notification for asynchronous state. Review custom HTTP subscriptions, timers, event listeners, modals, and cached routed pages. Remove reliance on `NgZone.run()` as the mechanism that makes a template update.

Merge the zoneless test setup. Remove custom `zone.js/testing` imports and adapt tests that depend on Zone.js-based timing helpers to explicit asynchronous waiting or the target runner's timers. Retain real signal properties in typed test fakes. **v3 still uses Jasmine/Karma**; the runner changes to Vitest in v4, so use the [v4 test migration notes](v4.md#5-convert-fork-owned-tests-to-vitest) when merging that source.

### Register custom icons centrally

Ionicons referenced by name are registered before browser and test bootstrap in `src/ionicons-polyfill.ts`. Import every additional fork icon and include it in that file's `addIcons()` call, preserving any names the templates use. Component-constructor registration is too late for icons already present in server-rendered HTML.

Check custom menu, toolbar, and content icons after a direct SSR page load and after browser navigation. See [icon registration](../DEVELOPMENT.md#registering-icons) for the current convention.

The completed [Stage 1 migration plan](../migrations/completed/angular-22-modernization/STAGE-1-STANDALONE-ZONELESS.md) records the implementation details for custom code that needs a closer comparison.

## 6. Preserve SSR fixes and the v3 output contract

v3.1.0 returns HTTP **404** when Angular renders the page-not-found wildcard route. Tests, monitors, or custom middleware that previously expected a 200 response for an unknown route must account for this correction. Check both the rendered page and the HTTP status.

[v3.1.1](../../CHANGELOG.md#311--2026-10-02) fixes an Ionic SSR memory leak present since v2.7.8 and updates Ionic to 9.0.6. Merge the dependency and lockfile changes rather than retaining the older fork pin. It also changes static collection-menu generation to share non-multilingual collection data and retry failed backend fetches; reconcile fork modifications to the generator and shared fetch helper.

The v3 production server remains the root `server.ts` using `CommonEngine`, with split browser/server builders, the `dist/app` layout, and the `dist/app/proxy-server.js` launcher. The standalone migration does not itself introduce the application builder, a `src/server.ts` source entry, or an ESM `server.mjs` launcher. When merging current upstream source, adopt those later changes together as described in [v4](v4.md).

## 7. Validate the edition after merging

Use the commands and contracts of the target source. For a v3.1 checkout:

1. Confirm Node/npm versions, run `npm ci`, and run `npm run test:ci`. Update custom standalone-component specs and asynchronous-state tests.
2. Run `npm run extract-i18n`; retain edition languages, titles, and existing translations.
3. Regenerate routes with `npm run generate-routes`, build with `npm run build:ssr`, and start with `npm run serve:ssr`. Run edition-specific SSR smoke checks and verify custom routes, guards, and locale prefixes.
4. Review home-page defaults in portrait and landscape, fonts, scoped overrides, and TEI text against the backend's actual HTML structure.
5. Verify that asynchronous UI state updates after responses and timers, including after leaving and returning to cached pages. Check all additional named icons on first page load and subsequent navigation.
6. Verify HTTP 404 responses for unknown routes, canonical URLs, static assets, and the edition's Docker/nginx deployment. If auth is enabled, verify login/session behavior and protected-route handling.

For current file locations and edition settings, use [project customization](../PROJECT-CUSTOMIZATION.md). For the next major release's changes, review [v4](v4.md) as part of the merge from upstream `main`; these release notes do not require deploying an intermediate v3 version.
